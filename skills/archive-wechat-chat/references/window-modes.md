# 微信窗口模式与观测

先判断当前材料来自哪一种窗口，再决定如何读取范围、消息顺序和边界。用户已经打开目标窗口时，先观察当前画面与可见来源线索；能据此判明就不要重复追问。标题只是线索，需结合进入路径、窗口内容和截图确认。只有无法判断用户指定的范围或来源时，才问一个简短问题。

始终由一个 agent 操作共享的微信窗口。子代理只读取已保存的截图、AX 文本和批次记录，不同时操作 UI。

主窗口是可持续收到新消息的实时会话；合并转发是聊天之后手动选取并转发的固定批次。合并转发的首要衔接问题是同一固定包内滚动页面的重叠归属，重复导入则用于验证同一包不被再次收录，并非等待包内实时追加。新转发包使用独立 `scopeId`，不能因群名相同自动接在旧包后面；如要关联，先核对原会话身份及实际选区重叠，保留明确关系证据。

| 模式 | 如何识别 | 可证明的范围 | 当前观测状态 |
|---|---|---|---|
| `main_chat` 主聊天会话 | 用户当前打开的参与者聊天窗口；结合会话内容与进入路径确认 | 仅用户指定且实际捕获到的会话范围；不因一个可见样本通过就扩展到完整历史 | 已完成 3 条可见消息样本的落盘、校验和重复导入 |
| `history_search` 聊天记录搜索 | 通过搜索词、日期或其他条件进入的结果列表；不是合并转发窗口 | 只证明当前查询返回并核对的结果。保留查询范围；不能据此称整段会话或全部历史已归档 | 已检查 Media 图片查看与 Save 面板；未完整抓取 |
| `merged_forward` 独立转发记录 | 通过打开收到的转发记录进入独立记录窗口；`Chat History for …` 或 `Chat History` 是可见线索，但标题本身不能单独定类 | 每份转发记录是独立范围，只证明其中实际捕获并核对的项目，不扩展到原聊天的其他消息 | 已完成一份 22 条记录的全范围采集、媒体导出、CLI 校验及重复导入 |

## 主聊天增量更新

- 首轮按用户指定范围建立底稿。已有 `main_chat` 档案后，“更新/继续归档”默认只处理增量，不再次从聊天最早端全量扫描；全量校验已有文件不等于重新抓取全历史。
- 先读取最新轮次、来源绑定和最后消息 ID，核对末条作者、正文、时间表示、引用及媒体 `captureId`。在同一实时会话内定位该出现位置，取少量尾部旧消息作为连续重叠，然后捕获其后的新消息。尾部内容重复时扩大重叠到足以区分出现位置，不做全局文本去重。
- 捕获开头必须与档案的一个精确尾部后缀相符，并包含最后已归档消息；传入该末条 `anchorId`。保留旧消息的正文、时间表示与媒体身份，不因本轮换了表情包占位策略而改写重叠部分。无法确认锚点时保留待核证据，先在同一会话有界查找，不自动改做全量重扫或接到同名转发包上。
- 为实时会话记录本轮截止消息及来源证据。抓取期间继续到来的消息可留给下一轮，不无限追赶移动的末端。本轮起点是已核验的衔接位置，终点是本次截止位置；无需再次证明群聊创建起点。
- 只把重叠后的新消息写入新轮次，旧轮次和 ID 不变，再校验并重建阅读页。确认没有新消息时报告新增 0 条，通常不创建空轮次；测试重复导入时允许在独立校验副本中验证零新增。

对固定 `merged_forward` 包，重复打开或导入仍是同一固定范围；新收到的转发包另有来源范围，不能默认接到主聊天或旧包后面。`history_search` 的结果可能随会话和查询变化，但仅证明实际核对的查询结果；它既不是固定转发包，也不自动等于主聊天全量或增量。可用搜索定位锚点，回到主聊天后重新确认来源和顺序。

## 已观察：主聊天可见块

主聊天窗口的 AX 包含 `chat_input_field` 和 `chat_message_list`。列表中每条消息的 AX 仅提供正文；引用可能另含 `Quote X's message:` 文本，但 AX 不提供主作者。时间以独立分隔项出现（例如 `17:34`），不是每条消息都有的精确时间。截图中群聊侧显示的别名可能不同于合并转发中的历史显示名；本人侧气泡不显示姓名。不得仅凭气泡方向推断实名。确认本人身份需要一次明确的资料或用户映射证据，否则保留待确认作者候选。

本次选取主窗口连续 3 条作者已核对的可见消息，涉及 2 个作者；独立范围首轮落盘 3 条、重跑新增 0 条，Markdown/JSON/HTML 与 CLI 校验通过。1 个引用精确匹配，1 个目标在样本之外而保留未匹配。没有验证完整主聊天的滚动和全部历史边界。消息正文、作者和时间只能按来源实际提供的证据记录；时间分隔项保留为上下文，不自动赋给每条消息。分别报告内容覆盖完整性与来源时间精度：没有逐条精确时间时，可将时间戳留空并保留分隔标签上下文，不能补造时刻；这本身不使内容范围不完整。缺作者证据或缺页仍须标记未完成。群聊别名与合并转发中的显示名分别保留；只有有证据支持时才记录二者关联。

## 已观察：独立转发记录

本次观察的独立窗口标题符合 `Chat History for …` 形式。AX list 提供每项正文及尾部时间（例如合成值 `2026-3-4 09:05`），没有主作者。截图中的各项显示作者和完整年月日。AX 对回复给出扁平正文、`引用作者:引用正文` 和时间；截图中的引用文字被截断时，AX 可补充完整引用文本，但必须先按正文、时间和窗口顺序与截图中的那一项对齐。AX 的顺序或气泡位置不能代替截图中的作者归属核验。合并转发中的群聊显示名不能静默替代主聊天截图里的群聊别名。

本次合并转发观察到 22 条记录，来自 5 个显示名，包含 2 张图片、1 个链接卡片和 6 条引用。向较新方向从顶部连续半页滚动至底部；终点有两次画面不变、滚动条到底和终止线等相互印证的来源内证据。条目计数本身不证明已完整落盘或通过校验。首尾项目可能只部分显示；新项目要先滚到作者完整可见再核验，AX 只有正文时不足以确认作者。

实际 7 页合并的重叠数为 `0,3,4,2,4,3,3`，去除跨页重叠后为 22 条。首轮落盘后，两次整批重跑及一次分页重跑均新增 0 条、总量保持 22；Markdown/JSON/HTML 生成与 CLI 校验通过。引用包括 5 个精确匹配及 1 个明确标为推定的链接标题匹配。截图证据来自会话工具而未落盘，验收记录保留此限制。本次样本未发现重漏，不保证任意记录绝对无遗漏。

反向滚动时，从末页向较旧方向移动半页，本次新见 3 条较早记录并与前页连续重叠 3 条。AX diff 可把新出现的较早项目放在 diff 输出末尾，因此 diff 输出顺序不是消息顺序。工具支持时获取禁用 diff 的完整 AX tree；否则按每页截图重建。每页始终按画面自上而下排列，向上捕获的批次只反转页批次顺序，不反转页内消息。临时 AX element ID 会刷新并重编号，不是稳定 message ID 或 captureKey。

单次画面稳定不能证明到达转发记录顶部、底部或用户要求的范围边界；本次底部判断依据终止线、滚动条位置和连续稳定画面等证据。图片保存和原图状态须根据这个独立窗口实际出现的控件判断；本次合并转发图片操作的兼容性证据见[图片保存说明](media-capture.md#已观察的兼容性)。

每页按画面自上而下记录。若通过向上滚动取得更早的批次，只反转批次的页面顺序，不反转任一页内部的消息顺序。每份转发记录各自成范围；不能仅因群名相同就把不同转发包拼成同一段。若无法确认两份记录是否相连，分别保留，并把关系记为待核候选。

相同作者、同一时间、相同正文仍可能是不同消息。字符串后缀/前缀相等不是出现位置相同的证明；必须结合截图位置、滚动连续性和相邻上下文核对重叠。无法分辨时保留待核证据并回滚重采，不自动删掉候选重复项。明确的人工重叠数量也必须附带实际位置证据，不能只把算法建议写成“已核对”。

## 每种模式都要记录的观察

- 用户请求的范围，以及实际打开的来源模式；有限结果集不得改写成整段会话。
- 捕获批次的前后顺序、可辨认的重叠项、每项的作者是否完整可见，以及 AX 文本和截图如何对齐。
- 每页内部的显示顺序与批次的时间顺序分别核对；独立转发包不因相同群名而合并。
- 起点与终点各自有什么来源内证据。相同画面、滚动无变化或到达当前可见列表末尾，只表示画面状态，不单独证明边界或完整性。
- 日期和时间在来源中实际显示到什么精度。能从可见日期分组可靠确认时才关联日期；不从导出日期、系统当前日期或消息相邻位置补造日期。分别报告内容覆盖完整性与时间精度；缺少逐条时刻不等于内容缺失，保留时间分隔上下文且不补造。缺作者证据或缺页则标记未完成。
- 图片在该模式下实际提供的打开、保存或原图操作。未观察到的操作记为未验证，不从其他模式推定。

UI 工具报告状态变化时，不能据此断定是用户切换了窗口；应用异步更新控件（例如 `Extract Text` 从 disabled 变为 enabled）也可能触发变化。立即重新获取完整 UI 状态，复核来源模式、标题和目标，再读取当前索引；不得复用旧索引。不同模式的导航和边界线索需分别实测。上述合并转发与主聊天样本的 CLI 验收，不替代其他设备、其他窗口类型或新消息持续到来的长期验证；历史搜索仍只检查了图片查看与 Save 面板。
